# DP_DBStorage

Серверный graft-мод DayZ: непрерывная копия хранилища сервера (`storage_<id>`: мир,
машины, постройки, игроки) в одном файле **SQLite** — с историей, откатом на любой
момент и автоматической починкой хранилища при старте. Работает поверх
[KR_GRAFTED](https://github.com/KRdayzmodding/KR_GRAFTED); внешняя СУБД не нужна.

Игра продолжает сохраняться так, как сохраняется без мода: в свои файлы, своим кодом.
Плагин её не подменяет и в её формат не вмешивается — он наблюдает за файлами и
забирает готовые. Поэтому патч DayZ не может «сломать базу»: в худшем случае плагин
перестаёт понимать новый формат и хранит файлы как есть, ничего в них не исправляя.

## Как это устроено

```
главный поток игры                    фоновый поток плагина              диск
──────────────────                    ─────────────────────              ────
движок пишет storage_<id>\*  ──┐
                               │ перехват CreateFileW:
                               │ «в storage была запись» (+1 к счётчику, ~30 нс)
                               └────────────►  пауза 1 с после последней записи
                                               прочитать изменившиеся файлы
                                               целые → одной транзакцией ──────►  <миссия>.storage_<id>.db
                                               оборванные → подождать             (поколение №N)
старт сервера, до первого чтения движком:
  чего нет на диске — из базы; оборванный слой — целой версией из базы
```

- **Главный поток** исполняет одну нашу функцию: перехват открытия файла на запись.
  В ней сравнение пути и увеличение счётчика — без памяти, блокировок, диска и базы.
  Всё остальное делает один фоновый поток с пониженным приоритетом.
- **Движок не ждёт плагин.** Если движок открывает файл, который плагин в этот момент
  читает, перехват повторяет открытие, а плагин бросает чтение и уступает.
- **Поколение** — одна транзакция: всё, что плагин забрал за проход, попадает в базу
  целиком или никак. Работающий сервер пишет мир не пачкой, а по одному файлу раз в
  ~1.3 с (цикл по всем файлам — 38 с, новый цикл каждые 52 с), поэтому поколение на
  нём — обычно один файл. Одинаковое содержимое хранится один раз (блобы адресуются по
  SHA-256), но на живом сервере каждый цикл меняет каждый файл: база растёт на один
  набор файлов мира за цикл, пока не упрётся в `keep_hours` или `max_db_mb`.
- **Игроки** (`players.db`) раскладываются построчно: персонаж = строка, меняется
  только то, что изменилось. Содержимое персонажа плагин не разбирает.
- **Параллельной записи нет намеренно.** Замер: два писателя в один файл SQLite не
  дают ничего (блокировка одна), а настройка одного писателя даёт ×9.5. Быстрее всего —
  один поток, одна транзакция на цикл.

## Скорость

`dpdb bench` на копии настоящего storage (SQLite 3.54.1, `synchronous=FULL`), лучший
из нескольких прогонов:

| Операция | 94 файла, 9.4 МБ, 5000 персонажей | ×20: 1880 файлов, 189 МБ |
|---|---:|---:|
| Первый захват (мир + все игроки) | 98 мс | 640 мс |
| Холостой проход (ничего не менялось) | 0.4 мс | 5.6 мс |
| Цикл сохранения (переписана треть файлов) | 9 мс | 159 мс |
| Сохранение игроков (изменилось ~60 из 5000) | 24 мс | 28 мс |
| Обычный старт (диск совпадает с базой) | 52 мс | 102 мс |
| Старт после полной потери storage | 243 мс | 3.4 с |
| Проверка всей базы (`dpdb verify`) | 16 мс | 178 мс |
| Перехват на главном потоке, на одно открытие на запись | 26–35 нс | 26–35 нс |

Всё, кроме последней строки, — время фонового потока. Игра платит только последнюю
строку. На больших объёмах всё упирается в диск (чтение файлов, запись журнала базы и
его сброс), и цифры плавают на треть от прогона к прогону; `dpdb bench` сам проверяет,
что замеряемое действительно сработало, и иначе завершается ошибкой.

Из чего складывается проход на 9.4 МБ и 5000 персонажах: чтение файлов 3 мс, SHA-256
всего содержимого 8 мс, запись в базу 5000 персонажей с блобами 13 мс, сброс журнала на
диск 1–18 мс по объёму. Чтение `players.db` игры — 12 мс: это её файл со страницами
4 КБ, и читается он каждый раз заново.

Старт после потери: слой CE пишется ~1 мс, файл мода без заголовка слоя — десятки мс
(ждём сброса на диск, иначе после сбоя питания его порчу не отличить; в ×20 таких
файлов 100).

На настоящем сервере (1.30.164289, свежий Chernarus, 31 файл): плагин готов через
17–51 мс после загрузки; после удаления всего `storage_<id>` мир восстановлен за 42 мс,
движок загрузил те же предметы.

## Что происходит при сбоях

| Ситуация | Что делает плагин |
|---|---|
| Сервер убит посреди сохранения, слой оборван | На старте заменяет слой последней целой версией из базы. Оборванный слой в базу не попадает никогда |
| Сбой питания, файл слоя из нулей | То же: пустышка на месте слоя заменяется целой версией |
| Пропал файл или весь `storage_<id>` | Возвращает из базы до того, как движок начнёт читать |
| `players.db` испорчен | Откладывает в `quarantine\`, собирает заново из базы |
| Испорчена сама база | Откладывает как `*.corrupt-<время>`, создаёт новую и заново забирает мир с диска. Сервер не останавливается |
| База недоступна, диск полон, ошибка плагина | Сервер работает как без мода. Причина — в `dp_dbstorage.log` и `DbStatus()` |
| Два сервера на одну базу | Второй не открывает базу (именованный замок) |

Правило старта: **что есть на диске и цело — главнее базы**. База закрывает дыры и
заменяет оборванное, но никогда не переписывает целый файл движка. Ни один файл не
пишется под настоящим именем наполовину (временный файл + переименование), ни один
блоб не попадает на диск без сверки хеша.

## Обновления игры

- **Формат содержимого плагин не знает.** Он знает одно: как по заголовку слоя CE
  отличить дописанный файл от оборванного (`src/format.cpp`, разбор относительно метки
  `STORAGE_`, а не по жёстким смещениям). Новая версия формата с тем же заголовком
  работает без правок.
- **Незнакомый заголовок** — файл хранится как есть и никогда не «чинится». Оборванный
  слой заменяется, только если в базе лежит целая версия того же файла с той же версией
  формата: разбор уже подтверждён настоящим файлом.
- **Смена сборки игры** — последнее поколение старой сборки закрепляется автоматически
  (удержание его не удалит): откат на состояние до патча доступен всегда.
- **Движок стал писать иначе** (перехват не видит записей) — плагин замечает это сам,
  пишет предупреждение и работает обходом каталога раз в `rescan_sec`. Данные в
  безопасности, выросла только задержка.
- **`players.db` сменил схему** — известные столбцы раскладываются построчно, остальная
  схема сохраняется как SQL; если разложить нельзя — файл хранится целиком.
- **Перехват один**: слот `CreateFileW` в таблице импорта `DayZServer_x64.exe` /
  `DayZDiag_x64.exe`. Сигнатур и адресов внутри движка нет — искать после патча нечего.

Факты о движке, на которых всё стоит, с адресами и номерами сборок:
[docs/research/dayz-persistence.md](docs/research/dayz-persistence.md).

## Установка

```powershell
graft install "C:\DayZServer"                        # ядро GRAFT, один раз
powershell -File deploy.ps1 -Game "C:\DayZServer"    # сборка + PBO + раскладка в @dbstorage
```

Запуск сервера с `-serverMod=@dbstorage`. Настройка не нужна: база появится в
`<профиль>\dp_dbstorage\<миссия>.storage_<id>.db`, журнал — `<профиль>\dp_dbstorage.log`.

Сборка без раскладки: `build.cmd release` → `out\release\DP_DBStorage.grafted.dll`,
`out\release\dpdb.exe`. Требования — в [CONTRIBUTING.md](CONTRIBUTING.md).

Собственные резервные копии движка (`storage_<id>\backup`) с плагином избыточны и
сами попадают в базу, раздувая её. Отключаются строкой
`<default name="backup_count" value="0"/>` в `<defaults>` файла `cfgeconomycore.xml` миссии.

## Настройка

`<профиль>\dp_dbstorage.cfg`, все ключи необязательны. Неизвестный ключ — ошибка:
файл игнорируется целиком, в журнале сказано почему.

```ini
enabled            = 1      # 0 — плагин не делает ничего
keep_hours         = 24     # глубина истории для отката
max_db_mb          = 8192   # потолок базы: при превышении история режется раньше
players_period_sec = 30     # не чаще — снимок players.db
rescan_sec         = 30     # страховочный обход каталога (и режим без перехвата)
db_dir             =        # где лежит база; пусто — <профиль>\dp_dbstorage
storage_dir        =        # каталог storage_<id>; пусто — определить по -mission/-config
```

Из скриптов: `string DbStatus()` — та же сводка, что в журнале.

## dpdb — утилита администратора

```
dpdb status  <база>                         сводка
dpdb gens    <база> [N]                     последние поколения
dpdb verify  <база>                         целостность базы и каждого сохранённого файла
dpdb export  <база> <поколение> <каталог>   выгрузить состояние поколения в каталог
dpdb pin     <база> <поколение> [заметка]   закрепить: удержание не тронет
dpdb unpin   <база> <поколение>

только при остановленном сервере:
dpdb restore <база> <поколение> [storage]   откатить хранилище к поколению
dpdb wipe    <база> world|players|all [storage]
dpdb bench   [storage] [--scale=N]          замер скорости на копии storage
```

Откат и вайп сами делают поколение «до» — отменить можно и их.

**Вайп — только через `dpdb wipe`.** Если удалить файлы из `storage_<id>` руками, на
следующем старте плагин примет это за потерю и вернёт их из базы.

## Движок базы

SQLite 3.54.1 собирается из официального исходника прямо в плагин и в `dpdb.exe`:
отдельной DLL нет, ставить нечего. На любой Windows работает один и тот же движок, а не
тот `winsqlite3.dll`, что оказался в системе (его версия зависит от сборки Windows).
Исходник закреплён ссылкой и хешем в [CMakeLists.txt](CMakeLists.txt); обновление —
новая ссылка и хеш со страницы загрузок sqlite.org плюс номер версии в
[tests/sqlite_test.cpp](tests/sqlite_test.cpp).

Сборка — с набором опций, который SQLite рекомендует сам: без учёта памяти
(`DEFAULT_MEMSTATUS=0`), без мьютексов на соединении (`THREADSAFE=2`: у нас одно
соединение — один поток), без устаревших API, общего кэша и загрузки расширений.
Настройки базы: WAL, страница 64 КБ, кэш 64 МБ, `synchronous=FULL` — коммит считается
сделанным, только когда он на диске.

Что показали замеры (чередующиеся прогоны, лучший из 9):

| Что меняли | Результат |
|---|---|
| Системная `winsqlite3.dll` 3.53.4 → своя сборка 3.54.1 | проход целиком: в пределах шума. Он упирается в диск и SHA-256, а не в SQLite |
| Опции сборки по умолчанию → рекомендованные | чтение строк −25 %, запись — в пределах шума |
| `THREADSAFE=2` → `0` (совсем без мьютексов) | разницы нет; оставлен безопасный вариант |
| `INSERT OR REPLACE` → `INSERT` для строк поколения | 20 → 1.2 мкс на строку: при включённых внешних ключах `REPLACE` заводит журнал оператора и копирует в него страницы по 64 КБ |
| Одна проверка `players.db` на старте вместо двух | −22 мс на каждый старт |

Итог двух последних строк: первый захват 237 → 98 мс, обычный старт 75 → 52 мс.

Обёртка над C API — своя, меньше 300 строк ([src/sqlite.cpp](src/sqlite.cpp)). Готовые
прослойки проверены на нашем горячем пути с той же сборкой SQLite (лучший из 15, мс):

| Прослойка | Запись 5000 персонажей | Чтение 5000 строк | 100 блобов по 256 КБ |
|---|---:|---:|---:|
| Голый C API | 13.2 | 0.96 | 18.1 |
| Своя обёртка | 12.7 | 0.93 | 17.6 |
| SQLiteCpp 3.3.3 | 12.6 | 1.12 | 17.4 |
| sqlite_modern_cpp | 13.1 | 1.26 | 17.3 |

На записи все равны: время уходит в сам SQLite. На чтении своя обёртка идёт вровень с
голым API, готовые медленнее на 15–30 % (копируют значения). Выигрыша от замены нет,
поэтому лишней зависимости в проекте нет.

## Пределы

- Файл, удалённый движком или модом в последнюю секунду перед остановкой сервера, на
  следующем старте вернётся из базы.
- Файлы больше 512 МБ не сохраняются (в сводке — «слишком больших»).
- В базе нет того, что движок не успел записать на диск, и того, что он записал в
  последние 1–2 секунды перед падением: плагин забирает файл через секунду после записи.
  Такой файл после сбоя берётся из предыдущего цикла (на 52 с старше).
- Глубина истории ограничена размером базы. Мир со слотом в 3.4 МБ даёт ~5.6 ГБ в
  сутки (замер); мир в 100 МБ, по оценке, упрётся в `max_db_mb = 8192` примерно через
  час, и история будет не длиннее этого часа. Прореживания старых поколений и сжатия пока нет.
- Только Windows.
